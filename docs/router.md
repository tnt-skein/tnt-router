# Маршруты

Приложение начинается с того, что запрос надо отдать нужному обработчику.
Сравнивать путь образцом по одному — просто, пока маршрутов десяток;
на сотне это становится заметной долей времени ответа, а на маршрутах
вида `/customers/:id/orders/:order` — ещё и источником ошибок.

Пакет `tnt-router` держит маршруты деревом и разбирает путь один раз.

Зависит от рока `http` — сервера, на который роутер ставится, — и от
`tnt-must`, `tnt-hash`, `tnt-clock`, `tnt-context`, `tnt-date`, `tnt-id`,
`tnt-log`, `tnt-fs`, `tnt-external` и `tnt-metrics`. Соседей `tnt-validate`
и `tnt-middleware` роутер берёт по имени, если они стоят: первый проверяет
ограничения параметров пути, второй разворачивает слои, названные именем.
Без них роутер работает: ограничения проверяются запасными образцами того
же смысла, а слоями бывают только функции.

## Как пользоваться

```lua
local router = require('tnt.router')

router.get('/customers/:id<int>', function(request)
    return router.json({ id = request.params.id, page = request.query.page })
end, { name = 'customer.show' })

router.group('/api/v1', { middleware = { 'rescue', { 'log', { level = 'info' } } } }, function(r)
    r.post('/customers', create)
    r.delete('/customers/:id<uuid>', remove)
end)

-- log_requests = false: строку запроса сервер пишет мимо фасада, с ?token=…,
-- и по умолчанию уровнем info. idle_timeout: без него у сервера нет срока
-- простоя, и соединение, шлющее заголовки по байту, держит файбер бессрочно.
-- В сеть такой узел выходит только за обратным прокси (см. «Выход в сеть»).
local httpd = require('http.server').new('0.0.0.0', 8080, { log_requests = false, idle_timeout = 60 })

-- Предел и срок тела запроса; без второго аргумента — мегабайт и минута.
router.attach(httpd, { max_body = 1024 * 1024, body_timeout = 60 })
```

Без `log_requests = false` сервер пишет строку каждого запроса встроенным
журналом уровнем `info`, со строкой запроса и её тайнами. С ним строка
уходит отладкой модуля `http.server`, туда же, где сервер пишет весь
запрос с заголовками. Процесс, которому нужен `level: debug`, держит
`http.server: info` в `log.modules` — подробности в документе
[tnt-log](https://github.com/tnt-skein/tnt-log).

Ответы собираются помощниками: `json`, `text`, `html`, `redirect`,
`no_content`, а тело по кускам — `stream` (см. ниже). Они есть и у модуля,
и у экземпляра: маршрутам приходит экземпляр, и `return route.html('<p>…</p>')`
пишется без второго `require`. Страница по шаблону — `route.view('about',
{ … })`: движок страниц (`tnt-template` или что угодно
с `render(name, data)`) приходит настройкой `view` при заведении,
и роутер не знает, чем рисуют страницы. Кусок страницы и страница
потоком — `route.fragment` и `route.view_stream`, метка версии ответа —
слой `router.etag()`, а данные, нужные каждой странице, — токен формы,
вошедший посетитель, — настройка `view_data` (см. «Страницы: целиком,
куском и потоком»).

Слоем бывает своя функция `(request, next)`, имя объявленного слоя или
пара «имя с настройками» — список уходит в `tnt.middleware` как есть, и
разворачивает его он. Без этого пакета рядом роутер понимает только
функции и говорит об этом при объявлении маршрута, а не при первом
запросе.

## Запрос

Запрос — таблица `{ method, url, path, query, headers, body }`,
разобранные параметры пути в `params`, разобранная форма в `form`
и `files` (см. «Форма и присланные файлы»), а чем запрос обслужен —
в `route`. Эти имена принадлежат роутеру: подложить их снаружи нельзя,
кроме `form` и `files` — их проверка вправе написать таблицей вместо тела.

**Всё остальное, что приложение положило в запрос, доезжает до слоёв
и обработчика как есть.** Опознанный оператор, адрес клиента, метка
развёртывания — роутер о них ничего не знает и ничего с ними не делает:

```lua
router.dispatch({ method = 'POST', path = '/login', identity = operator, peer = peer })
```

Отдельного места (`context`, `extra`) для них нет намеренно: довесок,
который едет рядом с запросом, теряется при первом же вызове в обход
обёртки — и теряется молча.

Адрес клиента `peer` роутер переносит и сам, когда подключён к серверу:
знает его один `http.server`, и дальше по цепочке взять его неоткуда,
а по нему считают неудачные попытки входа и пишут аудит.

## Тело запроса: предел и срок

`http.server` сам тело не ограничивает: читает столько, сколько назвал
`Content-Length`, и без срока, а его `idle_timeout` стережёт только
заголовки. Поэтому границу держит `attach`: тело читается до маршрута,
в пределах `max_body` и за `body_timeout`, и запрос вне пределов получает
отказ роутера — с записью в журнал и через обработчик отказов:

| Что пришло | Ответ |
|---|---|
| `Content-Length` больше `max_body` | 413, тело не читается вовсе |
| тело не пришло целиком за `body_timeout` | 408 |
| `Content-Length` не из одних цифр (`0x10`, `1e3`, `5, 5`) | 400 |
| `Transfer-Encoding` — тело кусками | 411: сервер его не читает |
| `Content-Length` нет | тело — пустая строка, как у самого сервера |

После такого отказа соединение закрывается, а недочитанное тело сервер
не дочитывает: иначе он сам прочёл бы заявленный гигабайт одной строкой,
а остаток разобрал бы следующим запросом.

```lua
router.attach(httpd, { max_body = 64 * 1024 })   -- API без загрузки файлов
```

Негодный предел — ноль, дробь, бесконечный срок — падает при подключении
и винит строку `attach`. `request.limits`, позванная сама, винит свою.

Кто обслуживает `http.server` своими маршрутами, без роутера, берёт то же
чтение отдельно. Читать тело надо первым делом и на каждом адресе,
до проверки входа: тело, которого
обработчик не прочёл, сервер дочитывает сам, сразу после обработчика и ещё
до ответа, — одной строкой, без срока и предела, — и отказ 401 гостю,
заявившему гигабайт, держал бы этот гигабайт в памяти узла.

```lua
local router = require('tnt.router')
local body_limits = require('tnt.router.request')
local limits = body_limits.limits({ max_body = 1024 * 1024 })

local body, failure = body_limits.body_of(request, limits)
if body == nil then
    -- Ответ — тот же, каким отвечает роутер; подробность в failure.reason —
    -- для журнала, а не для клиента.
    return router.refusal(failure)
end
```

## Форма и присланные файлы

Браузер шлёт форму двумя видами, и оба приходят телом: обычную — парами
`имя=значение` (`application/x-www-form-urlencoded`), форму с файлом —
частями с границей (`multipart/form-data`, RFC 7578). Разбирает их роутер,
до маршрута, и обработчик получает разобранное:

```lua
router.post('/customers', function(request)
    request.form.name          --> 'Иван'        поля формы
    request.form.tag           --> { 'a', 'b' }  повторённое имя — список
    request.files.avatar.name  --> 'кот.png'     присланные файлы

    return router.text('готово')
end)
```

- **`form` — поля, `files` — файлы**, и это две разные таблицы. Одна
  на оба смысла заставляла бы обработчик проверять, что пришло под именем
  `avatar` — строка или файл, — и промах в этой проверке уезжает
  в хранилище молча.
- **Тело, которое формой не назвали, остаётся телом.** JSON, текст, всё
  прочее доезжает до обработчика в `request.body` как есть; `form`
  и `files` у такого запроса пусты. Разбирать по догадке нельзя: однажды
  прочтётся как форма то, что ею не было.
- **Многочастное тело до обработчика не доходит**: оно разобрано
  на поля и файлы, и второй копии его в памяти нет — `request.body`
  у такого запроса пустая строка.
- **Повторённое имя — список**, как и в строке запроса: `tag=a&tag=b` —
  это два значения одного поля, а `shots` с двумя выбранными файлами —
  список из двух файлов.
- **Поле `<input type="file">`, в котором ничего не выбрали, не файл.**
  Браузер всё равно шлёт такую часть — с пустым именем и пустым телом, —
  и в `files` она не попадает: иначе обработчик сохранил бы файл в ноль
  байт с именем `file`.
- **Перекодировки нет.** Поле приходит байтами в кодировке формы (у всякого
  браузера последнего десятилетия это UTF-8); названная частью кодировка
  доезжает полем `charset`, а содержимое не трогается.

Проверка запроса без сервера пишет форму таблицей — разбирать в ней
нечего:

```lua
router.dispatch({ method = 'POST', path = '/customers', form = { name = 'Иван' } })
```

### Присланный файл

Файл — предмет с договором, а не строка в таблице:

| Поле или вызов | Что это |
|---|---|
| `client_name` | имя, как прислал клиент; ему не верят |
| `name` | безопасное имя: без пути, управляющих байтов и ведущей точки |
| `size` | размер, байт |
| `type` | тип содержимого, названный клиентом |
| `charset` | кодировка, названная клиентом |
| `field` | имя поля формы, в котором пришёл файл |
| `path` | где файл лежит; `nil` — файл в памяти |
| `file:read()` | содержимое целиком — пара `nil, err` при отказе |
| `file:move(куда)` | перенести на место — пара `nil, err` при отказе |

Отказ `read` и `move` — отказ `tnt-fs` как есть: таблица с родом
(`missing`, `denied`, `full` и прочие), причиной и текстом, которая
читается и строкой. Решают по роду: кончившееся место — `full`,
а не разбор текста системы.

```lua
router.post('/customers/:id/avatar', function(request)
    local file = request.files.avatar

    -- '../../etc/passwd' и 'C:\Users\Иван\кот.png' превращаются
    -- в 'passwd' и 'кот.png': пути в безопасном имени не остаётся.
    local moved, err = file:move('/var/lib/app/avatars/' .. request.params.id .. '-' .. file.name)

    if not moved then
        return nil, { status = 500, reason = err }
    end

    return router.json({ name = file.name, size = file.size })
end)
```

**Большой файл не держится в памяти.** Часть до `in_memory` (по умолчанию
64 КБ) копится строкой, а всё, что больше, пишется во временный файл
с правами `0600` и случайным скрытым именем — писателем `tnt-fs`,
кусками; тело при этом читается из соединения кусками, и в памяти узла
лежит один кусок, а не форма целиком. **Временный файл живёт до конца
обработки запроса** и убирается при всяком исходе — в том числе когда
обработчик упал или отказал. Часть, которую тело оборвало на середине
или которая упёрлась в предел, до обработчика не доходит, и её файл
убирается сразу, в разборе. Кому файл нужен дольше, есть `move`:
перенесённый файл уборка уже не трогает.

`move` переименовывает временный файл; другой том — копирует его
кусками и убирает исходник, а файл из памяти записывает. Копия и запись
ложатся подменой: читающий место видит прежний файл или новый целиком,
как и после переименования. Права у места — `0600` всяким путём.
Отказ переноса оставляет файл временным: уборка после ответа уберёт его,
как если бы переноса не было.

```lua
local moved, err = file:move('/var/lib/app/avatars/7.png')

if not moved and err.kind == 'full' then
    return nil, { status = 507, reason = err }   -- кончилось место
end
```

### Пределы формы

Задаются там же, где предел тела, — при подключении к серверу:

```lua
router.attach(httpd, {
    max_body = 12 * 1024 * 1024,   -- всё тело
    max_files = 4,                 -- файлов в форме
    max_file_size = 10 * 1024 * 1024,
    in_memory = 64 * 1024,         -- больше этого — временный файл
    temp_dir = '/var/lib/app/tmp', -- по умолчанию /tmp
})
```

| Настройка | Что значит | По умолчанию |
|---|---|---|
| `max_fields` | полей у обычной формы | 256 |
| `max_parts` | частей у многочастного тела | 64 |
| `max_field_size` | байт на одно текстовое поле | 256 КБ |
| `max_files` | присланных файлов в форме | 16 |
| `max_file_size` | байт на один файл | столько же, сколько на тело |
| `in_memory` | с какого размера файл уходит во временный | 64 КБ |
| `temp_dir` | куда класть временные файлы; пустая строка — тоже `/tmp` | `/tmp` |

Негодный предел — ноль, дробь, строка — падает при подключении, как
и `max_body`. Окружение роутер не читает: каталог временных файлов
называет приложение (`tnt-env` при сборке настроек), а не переменная
за его спиной.

Отказ по форме — такой же отказ на границе, как тело не в пределах:
он лежит в `request.refusal`, проходит слои входа, попадает в журнал
и рисуется обработчиком отказов приложения. Подробность (`reason`)
уходит в журнал, наружу — только код:

| Что пришло | Ответ |
|---|---|
| полей, частей или файлов больше предела | 413 |
| текстовое поле или файл больше своего предела | 413 |
| заголовки одной части больше 8 КБ | 413 |
| `multipart/form-data` без `boundary` | 400 |
| границы нет в теле, часть без имени поля, мусор за границей | 400 |
| часть с `Content-Transfer-Encoding: base64` | 400 |
| тело оборвалось посреди части | 400 |
| тело не пришло целиком за `body_timeout` | 408 |

### Проверка присланного файла

Размер, тип содержимого и расширение проверяет правило `tnt-validate`
(документ [tnt-validate](https://github.com/tnt-skein/tnt-validate), «Присланные файлы»):

```lua
local validate = require('tnt.validate')

local value, errors = validate.check(request.files, {
    avatar = validate.file({ max = 2 * 1024 * 1024, types = { 'image/png' }, extensions = { 'png' } }),
})
```

## Ответ по кускам

```lua
router.get('/audit/export', function()
    local after = 0

    return router.stream(function()
        local rows, err = audit_page(after)   -- страница записей со своей уступкой
        if rows == nil then
            return nil, err                    -- обрыв: клиент увидит незаконченный ответ
        end
        if #rows == 0 then
            return nil                         -- конец
        end
        after = rows[#rows].id
        return lines_of(rows)
    end, 200, { ['content-type'] = 'application/x-ndjson' })
end)
```

`produce` зовётся за каждым куском, пока не вернёт `nil`. Ответ уходит
с `Transfer-Encoding: chunked`, в памяти лежит один кусок, а медленный
клиент тормозит источник: между кусками сервер пишет в сокет и уступает.
За обратным прокси это так, только если ответ запретил прокси копить
поток (`x-accel-buffering: no`, см. «Выход в сеть»): иначе прокси
вычитывает выгрузку с узла целиком.

Отказ источника — `nil, err`, бросок или кусок не строкой — **рвёт
соединение без завершающего куска**. Кончить цикл было бы нельзя: сервер
закрыл бы тело как целое, и обрезанная выгрузка ушла бы клиенту
законченной. Подробность отказа уходит в журнал фасадом («поток ответа
оборван»), наружу — только обрыв. Пустые куски пропускаются: сервер
отправил бы пустой кусок завершающим.

**Поток говорит от имени своего запроса.** Тело сервер обходит, когда
обработчик уже вернул ответ, а слои входа вышли из своих областей, —
контекст файбера соединения к этому мигу пуст. Поэтому `stream` снимает
контекст запроса (`tnt-context`, `context.bind`) в миг сборки ответа
и ставит его на каждый шаг: записи источника, его обращения к соседям
и итог потока несут `request_id` и `trace_id` запроса, который собрал
ответ, а не того, кто обходит тело. Номер, названный клиенту
в `x-request-id`, находится и в записи об обрыве.

Итог потока фасад пишет сам, по концу тела:

| Запись | Уровень | Поля |
|---|---|---|
| поток ответа отдан | info | `seconds`, `bytes` |
| поток ответа оборван | error | `reason`, `seconds`, `bytes` |

`seconds` — от сборки ответа до конца потока, монотонными часами,
`bytes` — сколько байт отдал источник; под слоем сжатия это байты
до сжатия, а не на проводе. Запись слоя журнала («запрос прошёл»),
серверный отрезок трассы и ряды метрик кончаются с возвратом
обработчика, и выгрузка длиной в минуты числится там запросом
в микросекунды: сколько шла сама выгрузка, видно только здесь. Клиент,
ушедший посреди потока, не оставляет ни той, ни другой записи — сервер
узнаёт об уходе на записи куска и просто перестаёт звать источник.

Так это выглядит в журнале узла (вид JSON) за роутером со слоями входа
`request_id_header`, `request_id` и `log` из `tnt-middleware` и слоем
трассы `tnt-trace`; слои пишут под меткой приложения (`tag`
у `tnt-middleware`), здесь — `tnt.live`. Выгрузка шла по 0,5 с на кусок,
источник отказал на пятом куске; поля, которые добавляет встроенный
журнал (`time`, `pid`, `fiber_id`, `file`, `line` и прочие), опущены:

```
{"level": "INFO", "trace_id":"cb75152985886d94ac372e7fb65e4b89","fields":{"path":"/api/v1/audit","method":"GET","seconds":2.3387023247778e-05,"status":200},"request_id":"01M3FEZN845JSGXN3X40W6C8RY","message":"запрос прошёл","module": "tnt.live"}
{"level": "ERROR", "trace_id":"cb75152985886d94ac372e7fb65e4b89","fields":{"reason":"спейс app_audit снесён посреди выгрузки","seconds":2.0029610460042,"bytes":32},"request_id":"01M3FEZN845JSGXN3X40W6C8RY","message":"поток ответа оборван","module": "tnt.router"}
```

Клиент получил тот же номер заголовком `X-request-id: 01M3FEZN845JSGXN3X40W6C8RY`
и четыре куска без завершающего.

Без сервера тело обходится так же, как его обходит сервер:

```lua
for _, part in response.body do
    table.insert(parts, part)
end
```

Так устроена выгрузка журнала аудита: источник — `tnt.audit.stream.open`
из `tnt-audit`, кусок — одна выборка по GT с пределом и уступкой перед
ней, а между кусками источник держит только номер последней отданной
записи. Живьём журнал в 2000 записей (3,8 МБ) шёл клиенту, читавшему
100 КБ/с, кусками по 500 записей, а спейс, спрятанный посреди выгрузки,
оборвал её без завершающего куска: curl вышел с кодом 18, в журнале
узла — «поток ответа оборван» с причиной.

## Страницы: целиком, куском и потоком

```lua
local template = require('tnt.template')

local web = router.new({ view = template.new({ path = 'resources/views' }) })

web.get('/customers', function(request)
    local data = { names = names_of(request.query.q) }

    -- Кусок выбирает обработчик, и только из своего списка: имя куска,
    -- которого у страницы нет, — ошибка кода, то есть 500.
    if request.headers['x-fragment'] == 'rows' then
        return web.fragment('customers.index', 'rows', data, nil, { vary = 'x-fragment' })
    end

    return web.view('customers.index', data, nil, { vary = 'x-fragment' })
end)

web.get('/reports/year', function()
    return web.view_stream('reports.year', { rows = year_rows() })
end)
```

Три помощника экземпляра, и договор о типе содержимого у всех один —
`text/html; charset=utf-8`:

| Помощник | Что уходит | Движку нужно |
|---|---|---|
| `view(name, data, status, headers)` | страница целиком | `render(name, data)` |
| `fragment(name, section, data, status, headers)` | один кусок страницы, без рамки | `fragment(name, section, data)` |
| `view_stream(name, data, status, headers)` | страница по кускам | `stream(name, data)` — функция следующего куска |

Кусок страницы — тот же HTML, что и страница: сценарий страницы
вставляет его в открытую страницу и читает в той же кодировке. У страницы
потоком тип из кусков не выводится, а поток по умолчанию — поток байтов:
без названного типа браузер скачал бы страницу файлом. Поэтому поток
страницы собирает `router.response.html_stream`, а `router.stream`
остаётся потоком байтов для выгрузок.

Что такое кусок и как страница идёт потоком, решает движок
(например, [tnt-template](https://github.com/tnt-skein/tnt-template)).
Роутер знает только, что движок умеет: движку
без `fragment` или `stream` помощник отказывает словом —

```
движок страниц не умеет fragment
```

— а без настройки `view` — `страницы не настроены: нужен view в router.new`.
Это броски: и то и другое — ошибка того, кто собрал роутер, а не запроса.

**Кусок по заголовку — `vary` обязательно.** Один адрес тогда отвечает
двумя видами, и кэш по дороге, не знающий об этом, отдаст кусок тому,
кто открыл страницу, — после возврата «назад» посетитель увидит голые
строки таблицы. Заголовок, по которому выбран кусок, называется в `vary`
у обоих видов.

**Поток страницы рвётся, а не отвечает 500.** Первый кусок движок рисует
при вызове `view_stream`: ошибка страницы до него — обычный отказ 500
с опознавателем. Ошибка после — обрыв без завершающего куска (см. «Ответ
по кускам»): заголовки уже ушли, и сказать клиенту «500» нечем. За
обратным прокси поток идёт потоком, только если ответ запретил прокси
копить его (`x-accel-buffering: no`, см. «Выход в сеть»).

### Общие данные страниц: `view_data`

```lua
local web = router.new({
    view = views,
    entry = { sessions:layer(), csrf },                -- сессия в запросе, сверка токена
    view_data = function(request)
        return { csrf_token = request.session:token() }
    end,
})

web.get('/customers/new', function()
    return web.view('customers.form', { name = 'Иван' })          -- токен подмешан
end)

web.get('/preview', function()
    return web.view('customers.form', { csrf_token = 'образец' }) -- своё главнее
end)
```

Токен формы, вошедший посетитель, язык страницы нужны каждой странице.
Носи их каждый обработчик сам, забытое поле нашлось бы только открытием
той самой страницы: `@csrf` без токена падает при рисовании, и посетитель
получает 500. Настройка `view_data` — функция от запроса; её таблица
ложится под данные обработчика у всех трёх помощников — `view`,
`fragment` и `view_stream`. Данные обработчика главнее подмешанных:
страница, которой нужно своё значение, кладёт его сама. Сливаются они
в новую таблицу — ни таблицу обработчика, ни таблицу `view_data` роутер
не трогает: обработчик вправе отдавать одну и ту же на каждый запрос,
и токен, дописанный в неё, уехал бы в страницу другому посетителю.

**Считается на каждый вызов помощника**, а не при заведении роутера
и не на каждый запрос. Токен у каждой сессии свой, и посчитанный однажды
ушёл бы всем посетителям; а ответ JSON, который страниц не рисует,
не заводит сессии токен, которого не покажет.

**Запрос помощнику не передают** — `web.view(name, data)`, — и роутер
держит его сам: в хранилище файбера, на время ответа. Всего ответа,
а не одного обработчика: страница, которую рисует слой входа или свой
обработчик отказов, получает те же данные. Ключ — сам роутер, поэтому
помощник другого роутера чужого запроса не видит. Вне ответа —
в проверке, позвавшей помощник напрямую, или в файбере, заведённом
обработчиком, — запроса нет, и страница рисуется одними данными
обработчика.

**Отказ — парой `nil, err`**, и помощник отдаёт её как есть:
`return web.view(…)` вернёт её обработчиком, и роутер ответит статусом,
который отказ назвал (см. «Договор отказа на границе HTTP»). Пустота
и не таблица — поломка, и она бросается на первом же показе страницы:

```
view_data вернула nil, а не таблицу данных страницы
```

Не функция в настройке — отказ при заведении роутера:
`настройка «view_data» должна быть функцией, а не table`.

### Метка версии страницы: слой `etag`

```lua
local web = router.new({ view = views, middleware = { router.etag() } })

-- GET /customers                                  → 200, etag: "<crc32 тела>"
-- GET /customers, if-none-match: <та же метка>     → 304 без тела
-- GET /customers, if-none-match: "x", W/<метка>    → 304
-- GET /customers, if-none-match: <старая метка>    → 200 с телом и новой меткой
```

Страница, собранная заново на каждый запрос, без метки уходит целиком
всякий раз: браузеру, у которого та же страница уже есть, не с чем
сравнить. Слой ставит ответу метку — crc32 тела тем же видом, что
у раздачи файлов, — и на `if-none-match` с ней отвечает 304 без тела.
Метка сверяется тем же правилом RFC 9110 (13.1.2), что у раздачи:
списком, слабая пометка `W/` не мешает, `*` — любая. Метку, поставленную
обработчиком, слой не пересчитывает, а сверяет: версия данных бывает
известна и без тела. У куска страницы своя метка — тело другое, — и два
вида одного адреса кэш не спутает.

Слой трогает только ответ 200 с телом-строкой на GET и HEAD. У потока
тела заранее нет, и метки у него нет; на прочие способы совпавшее
условие RFC велит отвечать 412, и это дело обработчика. Место слоя —
маршрут или группа (`middleware`), а не вход (`entry`): на входе ответ
на HEAD уже без тела, и слой его пропускает — метка пустоты разошлась
бы с меткой ответа на GET.

Ответ 304 несёт те же заголовки, что и 200: по RFC 9110 (15.4.5) — всё,
чем клиент обновит запись в кэше (метку, `cache-control`, `vary`),
заголовки обработчика — куку — тоже, и тип содержимого. Тип — нарочно:
у ответа без него `http.server` ставит свой, `text/plain`, и кэш,
обновляющий запись по 304 (RFC 9111, 3.2), стал бы отдавать страницу
текстом. Длину у 304 сервер пишет свою — `Content-Length: 0`, — хотя
по RFC 9110 (8.6) там либо длина ответа 200, либо ничего; кэш по RFC 9111
её из 304 не берёт. Тип и длина у ответа без содержимого — недосмотр
`http.server` 1.9.1; тип слой ставит и тогда, когда рок его поправит, —
он тот же, что у ответа 200.

Слой бережёт сеть, а не узел: тело известно, только когда страница
нарисована, и рисуется она на каждый запрос, как и без слоя. Под слоем
сжатия, стоящим на входе, клиент с gzip получает метку слабой
(`W/"…"`): сжатое тело — другое представление. Назад он присылает её
с пометкой, слой снимает пометку при сверке, и 304 приходит ему так же.

## Смена протокола: `takeover`

Ответ 101 (WebSocket, RFC 6455) сервер написать не может: заголовок
`Connection` он выводит сам, из заголовков запроса, и `Upgrade` у него
становится `close`; дописывает `Content-Length: 0`; а после ответа читает
из соединения новый запрос HTTP там, где уже идут кадры. Поэтому ответ
с полем `takeover` — функцией, которой отдаётся соединение, — пишет
подключение роутера (`tnt.router.takeover`): голову ответа прямо в сокет,
и сразу зовёт `takeover(socket)` в файбере соединения.

```lua
router.get('/echo', function()
    return {
        status = 101,
        headers = { upgrade = 'echo', connection = 'Upgrade' },
        takeover = function(socket)
            socket:write('эхо:' .. socket:read(4, 5))
        end,
    }
end)
-- GET /echo → HTTP/1.1 101 Switching Protocols, connection: Upgrade, upgrade: echo;
-- дальше по сокету — «эхо:» и четыре присланных байта
```

Пока `takeover` идёт, сервер соединения не трогает; когда она вернулась,
сервер получает свой знак `DETACHED` и закрывает сокет, ничего в него
не дописав: жизнь соединения — это жизнь вызова. Слои видят такой ответ
как всякий другой — журнал пишет статус 101, заголовок опознавателя уезжает
в голову ответа. Заголовки идут по порядку имён, значение-список — несколькими
строками. Клиент, ушедший до головы ответа, до `takeover` не доходит
(«клиент ушёл до смены протокола» в журнал), упавший `takeover` соединение
просто кончает («соединение после смены протокола кончилось отказом»):
сказать клиенту по HTTP уже нечего. Без сервера (`dispatch` в проверке) поле
едет в ответе как есть.

## Параметры пути

| Запись | Что означает |
|---|---|
| `:id` | один участок пути |
| `:id<int>` | только цифры со знаком |
| `:id<uuid>` | только опознаватель |
| `:kind?` | участок необязателен |
| `*path` | весь остаток пути, вместе с косыми чертами |

Ограничение — часть маршрута, а не проверка внутри обработчика, и это
важно: запрос `/customers/абв` при `:id<int>` получает 404, а не 500
из глубины кода, который ждал число.

Значения параметров — **всегда строки**, раскодированные по участкам.
`%2F` внутри значения остаётся косой чертой и путь не разваливает.
Приведение типов — дело обработчика, через `tnt.validate`.

## Адреса

### Путь по имени

```lua
router.url('customer.show', { id = 7 })                                --> /customers/7
router.url('customer.index', nil, { tag = { 'a', 'b' }, page = 2 })   --> /customers?page=2&tag=a&tag=b
```

Без этого ссылки в панели собираются строками, и переименование пути
означает поиск по всему коду. С именами — одно место. Поля строки
запроса идут по порядку имён, а список — повторённым именем в порядке
списка: так его разбирает сам роутер (`tag=a&tag=b` — это `{ 'a', 'b' }`),
и собранное обратно разбирается в то же самое.

### Полный адрес: `full_url`

Письму с подтверждением, ссылке в ответе API и канонической ссылке
страницы нужен адрес со схемой и узлом. Схему и узел даёт настройка
`url` — адрес приложения:

```lua
local shop = router.new({ url = 'https://shop.example.org' })

shop.get('/customers/:id', show, { name = 'customer.show' })

shop.full_url('customer.show', { id = 7 })                      --> https://shop.example.org/customers/7
shop.full_url('customer.show', { id = 7 }, { tab = 'orders' })  --> https://shop.example.org/customers/7?tab=orders
```

**Схема и узел — из настройки, а не из запроса.** Узел своего имени
снаружи не знает: за обратным прокси он видит `http://127.0.0.1:8080`,
а клиент ходит на `https://shop.example.org`. Заголовок `Host`
и заголовки прокси (`X-Forwarded-Host`, `X-Forwarded-Proto`) пишет
клиент, если до узла он дошёл напрямую, и ссылка, собранная по ним,
уводила бы туда, куда скажет присланный запрос: письмо «сбросить пароль»
уходит настоящему владельцу, а ссылка в нём — на чужой сайт. Верить этим
заголовкам можно, только зная, что перед узлом стоит свой прокси, а это
знает развёртывание, не роутер, — поэтому роутер их не читает вовсе.
Адрес из настройки одинаков за прокси и без него, в запросе и вне
запроса — в работе очереди, которая шлёт письмо, запроса нет совсем.

- Адрес приложения — `http` или `https`, узел (с портом по надобности)
  и путь. Строка запроса, обрывок, пробелы и учётные данные
  (`user:pass@`) — отказ при заведении роутера: учётные данные ушли бы
  в каждое письмо.
- Путь — для прокси, который отдаёт узлу приложение под своим путём:
  `/shop/customers/7` снаружи — это `/customers/7` на узле. Тогда
  `url = 'https://example.org/shop'`, и полный адрес выходит с ним.
  Прокси, отдающий путь как есть, требует не пути в `url`, а `prefix`
  у маршрутов.
- Косая черта в конце снимается: `https://example.org/shop/` становится
  `https://example.org/shop`, и двух черт подряд в адресе не бывает.
- Без настройки `full_url` — бросок: «полный адрес не собрать: у роутера
  нет адреса приложения — настройка url». Нехватка настройки — промах
  того, кто собирал роутер, и заметить его надо на первом вызове,
  а не в письме, ушедшем с относительной ссылкой.

Отказ парой у `full_url` тот же, что у `url`: маршрута с таким именем нет,
параметр не задан.

### Подписанная ссылка: `signed_url` и слой `signed`

Ссылка в письме с подтверждением, ссылка на скачивание со сроком,
ссылка «отписаться» — это право на действие, выданное адресом. Без
подписи адрес переписывает кто угодно: `/invoices/7` меняется
на `/invoices/8`, срок — на год вперёд. Подпись делает адрес
неизменяемым: собрать её к подменённому адресу без ключа нельзя, а срок
входит в подписанное.

```lua
local crypto = require('tnt.crypto')

local web = router.new({
    url = 'https://shop.example.org',
    -- Ключ выводится из секрета приложения по назначению: у подписи ссылок
    -- он свой, и утечка ключа кук его не раскрывает.
    signing = { key = crypto.derive(secret, 'tnt.router.signed') },
})

web.get('/invoices/:id/download', download, { name = 'invoice.download', middleware = { web.signed() } })

web.signed_url('invoice.download', { id = 7 }, { expires = 3600, full = true })
--> https://shop.example.org/invoices/7/download?expires=1790283600&signature=HfJjmKtN-ZY1O2wmu7O915ryhAKTonVbzPPdozOBVsE

web.signed_url('invoice.download', { id = 7 }, { query = { list = 'news' } })
--> /invoices/7/download?list=news&signature=p3SXGEdLMSwmV9zTHB-iCSMeCQKLMuyOxADODK6bohU
```

| Настройка ссылки | Что значит |
|---|---|
| `query` | поля строки запроса: строка, число или их список; подписываются вместе с путём |
| `expires` | сколько секунд ссылка действует, от 1 до десяти лет; без него — бессрочно |
| `full` | полный адрес от `url`; без него — путь со строкой запроса |

Слой `signed()` пропускает к обработчику только ссылку со своей подписью
и в срок. Всё прочее — отказ парой, отказом границы HTTP со статусом 403,
и рисует его обработчик отказов приложения, как всякий другой:

```lua
-- /invoices/7/download?…            → 200 «счёт 7»
-- /invoices/8/download?… (подмена)  → 403
{"error":{"status":403,"code":"router_signature_invalid","message":"ссылка недействительна","incident":"2W1S-7JB7"}}
-- та же ссылка через час и секунду  → 403
{"error":{"status":403,"code":"router_signature_expired","message":"срок действия ссылки истёк","incident":"E1SV-4ECD"}}
-- в журнале: запрос отклонён … reason="срок действия ссылки истёк: ссылка действовала до 1790283600, а сейчас 1790283601" status=403
```

| Что с ссылкой | Код отказа |
|---|---|
| подписи нет, их две, подпись не сошлась | `router_signature_invalid` |
| подписанный срок записан не так, как его пишет подпись | `router_signature_invalid` |
| подпись сошлась, срок вышел | `router_signature_expired` |

Подделка и истёкший срок различаются кодом, а не номером: человеку
с устаревшей ссылкой приложение говорит «попросите новую», а с подменённой
— ничего подробного. Сначала сверяется подпись, потом срок: «срок истёк»
говорится только о своей ссылке. Без слоя — `web.verify(request)`,
та же сверка ответом `true` либо парой `nil, отказ`:

```lua
local ok, refusal = web.verify(request)
--> nil, { status = 403, code = 'router_signature_invalid', message = 'ссылка недействительна',
--        reason = 'в ссылке нет подписи' }
```

**Что подписано.** То, что читает обработчик, а не запись адреса: путь
одной записью и строка запроса, собранная заново из разобранных полей, —
со сроком и без самой подписи. Прокси, почтовый клиент и браузер вправе
переписать запись — `%7e` и `~`, `%d0%bf` и `%D0%BF`, `+` и `%20`,
порядок полей, `//` в пути, — и честная ссылка от этого не ломается;
а подмена того, что видит обработчик — участка пути, поля, значения,
лишнего поля, — ломает подпись. Подпись — HMAC-SHA256 от `tnt-hash`
в base64url без набивки, 43 знака, которые ложатся в адрес без
кодирования; сверка — за постоянное время. Перед подписанным стоит метка
назначения, и значение, подписанное тем же ключом для другого дела
(подписанная кука), подписью ссылки не станет.

**Что не подписано: схема, узел и способ.** Узел за прокси видит свой
адрес, а не тот, что в ссылке, и сверить узел ему не с чем: одна и та же
ссылка открывается и через прокси с его путём, и напрямую к узлу. Способ не подписан, чтобы одна ссылка служила
и странице, и кнопке на ней: ссылку «отписаться» из заголовка письма
почтовый клиент открывает POST, а человек — GET (RFC 8058). Где способ
важен, слой ставят на маршрут нужного способа, а не на группу.

**Срок — по стенным часам.** В ссылке — секунды эпохи (`expires`),
округлённые вверх: ссылка живёт не меньше обещанного. Выдаёт её один
узел, а открывают на другом и после перезапуска, поэтому монотонные
часы не годятся, а часы узлов обязаны идти вместе (NTP): узел, спешащий
на минуту, закрывает ссылки на минуту раньше.

**Ключ.** Не короче 32 байт: ключ HMAC короче свёртки ослабляет подпись
(RFC 2104), а короткий ключ в настройках — почти всегда `secret` или
пароль, набранный руками. Случайные байты дают `crypto.key()` один раз
в настройки либо `crypto.derive(секрет, назначение)` при запуске
(документ [tnt-crypto](https://github.com/tnt-skein/tnt-crypto)). Ключ живёт в замыкании подписчика: в `status()`
и в обходе роутера `pairs` его нет — только признак `signing = true`.

Ключ меняют, не ломая разосланных ссылок: подписывает `key`, а сверяют
по очереди `key` и `previous`.

```lua
local web = router.new({ signing = { key = fresh_key, previous = { old_key } } })
```

Прежний ключ убирают, когда истёк срок всего, что им подписано; каждый
лишний прежний ключ стоит чужой ссылке одного HMAC.

**Ошибки программиста — бросок** с виной на строке вызова: роутер без
`signing` (`signed_url`, `verify` и `signed()` бросают «у роутера нет
ключа подписи — настройка signing»), короткий ключ, незнакомая настройка
ссылки, срок вне пределов, поле строки запроса не того вида. Имена
`expires` и `signature` принадлежат подписи:

```lua
web.signed_url('invoice.download', { id = 7 }, { query = { expires = 1 } })
--> настройки ссылки.query.expires — имя занято подписью: срок задаёт настройка expires
router.new({ signing = { key = 'secret' } })
--> signing.key — ключ подписи не короче 32 байт, а не ключ из 6 байт
```

### Канонический адрес страницы: `canonical`

Одну страницу открывают по многим адресам: с меткой рассылки
(`?utm_source=…`), с порядком сортировки, с `//` в пути, по второму имени
узла. Поисковик считает их разными страницами и делит между ними вес,
а `<link rel="canonical">` называет одну. `canonical(request, opts)`
собирает её из адреса приложения, пути одной записью и только названных
полей строки запроса — тех, что меняют содержимое страницы:

```lua
local site = router.new({ url = 'https://shop.example.org', view = views })

site.get('/articles/:slug', function(request)
    return site.view('article', { article = find(request.params.slug), canonical = site.canonical(request, { query = { 'page' } }) })
end)

-- GET /articles//%d0%bf?page=2&utm_source=mail
--> canonical = https://shop.example.org/articles/%D0%BF?page=2
```

В шаблоне адрес идёт экранированным выводом — `&` между полями становится
`&amp;`, как и положено в значении атрибута:

```html
<link rel="canonical" href="{{ canonical }}">
<!-- <link rel="canonical" href="https://shop.example.org/articles?page=2&amp;sort=new"> -->
```

Общих данных страницы у шаблонов пока нет, и адрес кладут в данные
каждой страницы сами. Без `url` — бросок, как у `full_url`.

## Отказы

| Что случилось | Ответ |
|---|---|
| маршрута нет | 404 |
| маршрут есть, способ другой | 405 с заголовком `Allow` |
| запрос не разобран | 400 |
| обработчик упал | 500 с опознавателем происшествия |
| обработчик вернул `nil` | 500 с опознавателем происшествия |
| обработчик вернул `nil, err` | 500, а если `err` назвал свой статус — этот статус |
| слой `signed`: подписи нет или она не сошлась | 403 с кодом `router_signature_invalid` |
| слой `signed`: срок подписанной ссылки вышел | 403 с кодом `router_signature_expired` |

Заголовок `Allow` при 405 — не украшение: по нему клиент понимает, что
путь верный, а метод нет, и это единственный способ отличить «нет такого
адреса» от «сюда так нельзя».

**Пустота от обработчика — всегда поломка.** Не «нет такого адреса»:
маршрут-то нашёлся, иначе до обработчика бы не дошли. Знает, что искомого
нет, только он сам — он и обязан сказать это ответом (`router.files` так
и делает). Договор здесь общий с `tnt.middleware`: проход слоёв читает ту
же пустоту как «слой потерял ответ», и толковать её по-разному значит
отвечать на один и тот же промах то 404, то 500 — смотря обёрнут маршрут
слоями или нет.

Обработчик по умолчанию намеренно скуп: ни стеков, ни текстов чужих
отказов наружу. Свой подставляется одним вызовом, и отказ приходит ему
первым аргументом, запрос — вторым:

```lua
router.on_error(function(failure, request)
    return router.html(('<h1>%d</h1><p>%s</p>'):format(failure.status, failure.message), failure.status)
end)
```

Опознаватель происшествия есть у каждого отказа роутера, и по нему
находится запись журнала — подробности лежат там:

```lua
router.dispatch({ method = 'GET', path = '/nowhere' }).body
--> {"error":{"status":404,"message":"нет такого адреса","incident":"4KJ7-QW9M"}}
-- в журнале: запрос отклонён incident=4KJ7-QW9M method=GET path=/nowhere status=404
```

Опознаватель — восемь случайных знаков азбуки Крокфорда двумя группами:
человек диктует его дежурному по телефону, а `uuid` в тридцать шесть
знаков вслух не читается. Вид общий с пакетом отказов приложения:
их номера стоят в одном поле одного ответа. Азбука берётся у `tnt-id`,
случайность — у ядра (`digest.urandom`, подменяется как внешняя
зависимость `random`); ULID здесь не годится: время в старших знаках
выдало бы снаружи, когда узел отказал. Сам пакет отказов роутеру
не нужен — свой минимум роутер отдаёт и без него.

Поломка обработчика пишется в ту же запись вместе со стеком места
броска — полем `traceback`, рядом с причиной:

```lua
router.get('/customers/:id', function(request)
    error('таблицы нет')
end)

router.dispatch({ method = 'GET', path = '/customers/7' }).body
--> {"error":{"status":500,"message":"внутренняя ошибка","incident":"1XVE-9DBV"}}
-- в журнале: запрос отклонён incident=1XVE-9DBV method=GET path=/customers/7
--   reason="app.lua:2: таблицы нет" status=500
--   traceback="\nstack traceback:\n\t[C]: in function 'error'\n\tapp.lua:2: in function <app.lua:1>\n\t…"
```

Бросок роутер ловит `xpcall`, и ловушка снимает стек там, где он ещё
есть: после перехвата стек размотан, и запись говорила бы, что
сломалось, но не как туда пришли. Причина остаётся прежней строкой,
по которой запись и ищут, а стек нужен тому, кто её нашёл, — поэтому
он лежит своим полем. У маршрута со слоями
[tnt-middleware](https://github.com/tnt-skein/tnt-middleware) бросок
ловит конвейер и отдаёт отказом со стеком в поле `traceback`; снять
стек роутеру уже нечем, и он пишет принесённый, а причина тогда —
«обработчик упал: …». Чужой стек узнаётся по одному признаку — строке
в поле `traceback` таблицы-причины, прочитанной мимо метатаблицы.
Отказ, пришедший со своим опознавателем, в журнале уже описан тем, кто
отказал, и его стек второй раз не выписывается: вторая копия — вдвое
больше строк без нового смысла.

## Слои на входе

Слои из `middleware` оборачивают обработчик найденного маршрута:
отказы самого роутера — 404, 405, тело не в пределах — случаются
до них. Слоям, которым нужен каждый запрос, включая запрос на путь,
которого нет, есть другое место — `entry`, вокруг всего, чем роутер
отвечает:

```lua
local api = router.new({
    entry = { 'request_id_header', 'request_id', 'log', mode:layer() },  -- вокруг всего
    middleware = { authenticated },                                       -- вокруг обработчика
})
```

Первый на это место — опознаватель запроса с журналом: запрос
по несуществующему адресу уходит с `x-request-id` и записью, и человеку,
которому «ответило 404», есть что назвать. Второй — режим обслуживания
(`tnt-downtime`): закрытое приложение отвечает 503 и на `/nowhere`, иначе
по 404 снаружи читались бы его маршруты. Договор слоя тот же,
`(request, next)`; отказ парой `nil, err` рисует `on_error`, как и отказ
обработчика, — клиент не должен различать, кто именно ему отказал.
Слой, нужный не всякому запросу, ставится с фильтром по пути и способу
(`{ 'cors', { origins = { … } }, path = '/api' }`, документ
[tnt-middleware](https://github.com/tnt-skein/tnt-middleware)).
Межсайтовым заголовкам место именно здесь: на `OPTIONS` к существующему
пути роутер отвечает сам — 204 с `Allow` и без разрешений, — и слой
вокруг обработчика маршрута предварительного запроса не увидит.

Запрос на входе уже разобран, но маршрут ещё не найден: `params`
и `route` в нём пусты. Тело не в пределах (400, 408, 411, 413 у `attach`)
тоже проходит слои входа — у такого запроса есть голова, а отказ лежит
в его поле `refusal`; маршрут для него не ищется, слой входа отказ видит
и вправе ответить иначе. Мимо слоёв входа отвечается одно: `dispatch`
не с таблицей — отдать слоям нечего, а 400 тут промах вызывающего,
не клиента.

## Ряды метрик

Каждый ответ роутера — и найденного маршрута, и 404, 405, и тела
не в пределах, и поломки обработчика — ложится в ряды реестра
встроенного `metrics` (документ [tnt-metrics](https://github.com/tnt-skein/tnt-metrics),
«Прикладные ряды»). Меряет его то место, через которое идёт всякий разобранный
запрос, — и по сети через `attach`, и таблицей в `dispatch`:

| Ряд | Род | Метки | Что значит |
|---|---|---|---|
| `http_requests_total` | counter | `method`, `route`, `code` | сколько запросов обслужено |
| `http_request_duration_seconds` | histogram | `method`, `route` | сколько шёл ответ: от разбора до готового ответа |

Шесть заказов, четыре поиска и пятьдесят запросов сканера по путям,
которых нет, в выкладке живого узла:

```
http_requests_total{route="/orders",method="POST",code="202",alias="series-001-a"} 6
http_requests_total{route="/articles",method="GET",code="200",alias="series-001-a"} 4
http_requests_total{route="_unmatched",method="GET",code="404",alias="series-001-a"} 50
```

- **Маршрут — шаблоном**, `/customers/:id<int>`, а не путём: путей
  столько, сколько опознавателей в адресах, а шаблонов — сколько
  объявлено маршрутов. HEAD, обслуженный маршрутом GET, идёт шаблоном
  этого маршрута со способом `HEAD`.
- **Запрос без маршрута — словом `_unmatched`**: 404, 405, тело
  не в пределах и отказ слоя входа, до маршрута не дошедший. Путь
  сканера в метке завёл бы по ряду на каждую его попытку — пятьдесят
  разных путей выше легли одной строкой.
- **Способ — из списка** `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`,
  `OPTIONS`: его пишет клиент, и незнакомый идёт словом `_other`.
- **Код — строкой статуса ответа**; ответ без статуса — `200`, как его
  отдаёт сервер. Потолок — шестьдесят кодов, маршрутов — пятьсот; сверх
  потолка — `_other`.
- **Длительность — до готового ответа**, монотонными часами. Тело потока
  (`stream`) пишет сервер уже после, и в длительность оно не входит —
  его длительность лежит в итоговой записи потока (см. «Ответ
  по кускам»); у смены протокола меряется ответ 101, а не жизнь
  соединения.

Ряды общие на процесс: два роутера одного узла — приложение и панель —
кладут в одни ряды, и различают их шаблоны маршрутов.

## Договор отказа на границе HTTP

Свой обработчик отказов подставляется одной строкой потому, что отказ
роутера — не его частное устройство, а договор, общий с пакетом отказов
приложения [tnt-error](https://github.com/tnt-skein/tnt-error):

```lua
{
    status = 405,                              -- обязательно: число, 4xx или 5xx
    message = 'этот способ здесь не поддерживается',  -- слово для человека
    code = 'customer.gone',                    -- код из каталога, если он есть
    incident = '4KJ7-QW9M',                    -- номер уже сделанной записи журнала
    headers = { allow = 'GET, HEAD, OPTIONS' },-- заголовки, которых требует статус
}
```

Обязательное здесь одно — **числовой `status`**. По нему отказ и узнаётся:
не по виду строки, не по набору полей. `{ status = 'ok' }` и запись работы
`{ status = 1 }` отказом не считаются, успешный статус — тоже.

Договор читается в обе стороны.

**Наружу.** Роутер кладёт в отказ слово и заголовки, а не только в свой
ответ. Иначе чужой обработчик ответил бы «внутренняя ошибка» на промах
по адресу, а `Allow` при 405 — тот самый, которого требует RFC 9110, —
пропал бы молча: он ведь лежал в ответе, который чужой обработчик собрал
заново. Обработчику отказов, получившему такой отказ, остаётся сохранить
его статус и заголовки и не выдавать второго опознавателя: запись
в журнал уже сделал роутер.

**Внутрь.** Отказ, который вернул обработчик парой `nil, err`, роутер
читает по тому же договору: назвал свой статус — при нём и остаётся.
`nil, { status = 410, code = 'customer.gone', message = 'клиента больше нет' }`
отвечает 410, а не 500. Решать
за обработчика, что его «клиента больше нет» — поломка узла, роутеру
не по чину. Чужая строка и объект `box.error` статуса не называют
и становятся 500, а сам `err` наружу не уходит ни в каком
случае: подробности пишутся в журнал.

Отказ роутера остаётся при этом ответом и без всякого соседнего пакета:
`router.refusal(failure, request)` — та же функция, которой роутер
отвечает сам. Она нужна своему обработчику, который берёт на себя только
часть отказов:

```lua
router.on_error(function(failure, request)
    -- Под API отвечает свой вид отказа — там тело разбирает клиент;
    -- про всё остальное роутер говорит сам.
    if request ~= nil and request.path:startswith('/api') then
        return router.json({ problem = failure.code or 'failure', text = failure.message }, failure.status)
    end

    return router.refusal(failure, request)
end)
```

## Раздача файлов

```lua
-- Каталог сборки под началом пути: объявление на GET — HEAD роутер
-- обслуживает сам, на прочие способы дерево отвечает 405.
router.serve('/build', 'public/build', { immutable = true })

-- Каталог public целиком, как корень сайта: хвост ловит то, чего
-- не поймали объявленные маршруты, а более длинный путь важнее хвоста.
router.serve('/', 'public')

-- Панель, упакованная в модуль: обработчик собирается отдельно
-- и вешается на свой шаблон с хвостом.
router.get('/panel/*path', router.files({ bundle = panel, fallback = 'index.html' }))
```

Объявление и обработчик — разные вызовы, и это нарочно: `serve` заводит
маршрут (шаблон с хвостом, способ, имя), `files` собирает обработчик
из настроек. Одно имя на оба смысла — «собери обработчик» и «объяви
маршрут» — читается по-разному в зависимости от аргументов, а обработчик
нужен и сам по себе: панель вешает его на свой шаблон, приложение —
на группу со слоями.

Файлы берутся из каталога (`root`) или из памяти процесса (`bundle`):
упакованная в модуль панель приезжает вместе с кодом, и брать её с диска
на боевом узле неоткуда, а собранные из SCSS стили пересобираются
на каждую правку, и паковать их в модуль значило бы пересобирать узел.

### Что уходит клиенту

```lua
local serve = router.files({ root = 'public/build', immutable = true })
local ask = function(method, path, headers)
    return serve({ method = method, params = { path = path }, headers = headers or {} })
end

local first = ask('GET', 'assets/app-BX7Yy2Qk.css')
-- 200, тело файла и заголовки:
--   content-type:  text/css; charset=utf-8
--   cache-control: public, max-age=31536000, immutable
--   etag:          "586f72a5"
--   last-modified: Sun, 20 Sep 2026 09:36:45 GMT

ask('GET', 'assets/app-BX7Yy2Qk.css', { ['if-none-match'] = first.headers.etag })
-- { status = 304, headers = { etag = …, ['cache-control'] = …, ['last-modified'] = …, ['content-type'] = … } }

ask('GET', 'assets/app-BX7Yy2Qk.css', { ['if-modified-since'] = first.headers['last-modified'] })
-- 304: тела нет и здесь

ask('HEAD', 'assets/app-BX7Yy2Qk.css')   --> 200, те же заголовки и content-length файла, тело ''
ask('POST', 'assets/app-BX7Yy2Qk.css')
--> nil, { status = 405, message = 'этот способ здесь не поддерживается', headers = { allow = 'GET, HEAD' } }
ask('GET', 'assets/none.css')            --> nil, { status = 404, message = 'нет такого адреса' }
ask('GET', '../etc/passwd')              --> nil, { status = 404, message = 'нет такого адреса' }
ask('GET', '.env')                       --> nil, { status = 404, message = 'нет такого адреса' }
```

Тип содержимого берётся из таблицы рока `http` (`http.mime_types`,
полтысячи расширений) — поэтому рок `http` стал зависимостью пакета.
Поверх неё лежат свои строки: `charset=utf-8` у `css`, `html`, `js`,
`json`, `map` и `txt`, `image/x-icon` вместо устаревшего вида у `ico`,
и то, чего в таблице нет, — `map`, `webmanifest`, `woff2`. Незнакомое
расширение и имя без расширения — `application/octet-stream`.

Способ не тот — отказ парой `nil, { status = 405, message, headers = { allow } }`,
а не готовый ответ: 405 рисует обработчик отказов приложения — тот же,
что рисует 405 от дерева маршрутов, — и он же пишет о нём в журнал.
Слово лежит в отказе по той же причине, что у отказа «файла нет» (см.
ниже).
До этой ветки доходит только раздача, объявленная на все способы
(`router.any`): маршрут `serve` объявлен на GET, и 405 там собирает
дерево, с полным перечнем (`GET, HEAD, OPTIONS`).

`HEAD` — это `GET` без тела: заголовки те же, тело пустое, а файл ради
него не читается — ни с диска, ни кусками. Длину при этом называет сама
раздача (`content-length` — размер файла из снимка набора или из
`lstat`): по RFC 9110 (9.3.2) заголовки ответа на `HEAD` — это заголовки
ответа на `GET`, а сервер, которому досталось пустое тело, поставил бы
ноль. На `GET` длины в заголовках раздачи нет: строку меряет сервер,
а у ответа по кускам длины не бывает вовсе. До клиента настоящая длина
доедет с правкой рока `http` (см. «Опасные места»).

### Метка версии, время правки и 304

Метка — crc32 содержимого. У набора в памяти она считается **один раз,
при сборке раздачи**: иначе crc32 по всей панели платил бы каждый
запрос, в том числе тот, что получит 304 без тела. Набор при этом
снимается копией — файл, подменённый в таблице после сборки, раздача
не увидит (иначе он уходил бы со старой меткой, и браузер с прошлой
копией получал бы 304 на новое содержимое). Имя и содержимое каждой
записи обязаны быть строками — иначе отказ при объявлении маршрута:

```lua
router.files({ bundle = { 'app.js' } })
-- ошибка: имя файла в bundle должно быть строкой, а не number
```

Файлу с диска метка считается на каждый запрос: запомнить её можно было
бы только по времени правки, а оно у `fio` на macOS в целых секундах
(на Linux с дробью, но заголовок его всё равно несёт целым), и файл,
переписанный за ту же секунду без смены размера, сохранил бы старую
метку. Файл при этом всё равно читается целиком — но только пока он
меньше предела (см. ниже): у большого файла метка считается по размеру
и времени правки (`"1964-6aafa92d"`), потому что читать гигабайт ради
crc32 значит сделать ровно то, ради чего ответ и режется на куски.

Время правки уходит заголовком `last-modified` — у файлов с диска;
у набора в памяти времени правки нет вовсе, и заголовка тоже. Уходит
оно целыми секундами: дробь, которую `fio.lstat` отдаёт на Linux,
отбрасывается вниз — с ней файл выходил бы новее любой даты
`if-modified-since`, которую браузер присылает назад, и 304 не приходил
бы никогда.

Свежесть копии клиента проверяется по правилам RFC 9110: метка главнее
времени, и, когда пришёл `if-none-match`, время не спрашивается вовсе.
Метка сверяется по списку и без слабой пометки — `W/"…"`, `"a", "b"`,
`*` понимаются как положено: равенство строк целиком давало бы 200
с телом там, где хватает 304 без него. Слабой метку делает, например,
слой сжатия: клиенту с gzip он отдаёт её с пометкой `W/`, и с ней же
браузер приходит за файлом снова. В сам ответ 304 уходят метка,
время правки и срок жизни копии: по RFC он обязан нести всё, чем клиент
обновит свою запись в кэше. И тип содержимого: без него `http.server`
поставил бы `text/plain`, и кэш, обновляющий запись по 304 (RFC 9111,
3.2), отдавал бы стили текстом — браузер таких стилей не применит.

### Срок жизни копии

По умолчанию `cache-control: no-cache` — это не «не кэшировать», а
«спроси, не изменилось ли»: браузер держит файл у себя и приходит
с меткой. Обратное умолчание — вечный кэш — однажды оставляет половину
операторов на панели прошлой версии.

Файлу, у которого отпечаток содержимого стоит в имени, вечный кэш
не грозит ничем: он не меняется — меняется имя. Такому файлу раздача
отдаёт `public, max-age=31536000, immutable`, но только если её об этом
попросили:

```lua
router.serve('/build', 'public/build', { immutable = true })
-- app-BX7Yy2Qk.css → public, max-age=31536000, immutable
-- app.css, app.min.css, app-BX7Yy2Q.css → no-cache

-- Сборщик ставит отпечаток в начало имени? Образец — настройка.
router.serve('/build', 'public/build', { immutable = true, fingerprint = '^([%w]+)%-' })
```

Отпечатком считается кусок из восьми и более знаков азбуки base64url,
отделённый чертой или точкой и стоящий перед расширением. Правило
намеренно строгое и по умолчанию выключено: год кэша, выданный файлу
без отпечатка, чинится только у каждого клиента по отдельности.

### Большие файлы: ответ по кускам

Файл больше `in_memory` (по умолчанию мегабайт) в память не читается,
а уходит кусками по `chunk` байт (по умолчанию 64 КБ) — обычным ответом
роутера по кускам (см. «Ответ по кускам»):

```lua
router.serve('/downloads', 'public/downloads', { in_memory = 256 * 1024, chunk = 32 * 1024 })
```

Файл открывается читателем `tnt-fs` до ответа, а не на первом куске:
исчезнувший между опросом и открытием — это «файла нет» (`missing`),
а не 200 с оборванным телом. Открытый файл переживает удаление и уходит
целиком. Дескриптор живёт между кусками и закрывается на последнем;
клиент, ушедший посреди выгрузки, оставит его до сборки мусора — обрыв
роутер видит броском, и закрыть файл ему негде. Файл, переставший
читаться посреди ответа, рвёт соединение без завершающего куска:
кончившийся источник сервер закрыл бы как целое тело, и клиент принял
бы обрезанный файл за полный. Причина обрыва — отказ `tnt-fs` — уходит
в запись «поток ответа оборван».

Кусок — от одного байта до 64 МБ, границы читателя `tnt-fs`. Сверяются
они при объявлении маршрута: иначе читатель бросил бы на первом запросе
большого файла, в бою.

```lua
router.serve('/downloads', 'public/downloads', { chunk = 128 * 1024 * 1024 })  -- app/http.lua:40
-- ошибка: app/http.lua:40: настройка «chunk» должна быть числом от 1 до 67108864,
--         а не 134217728
```

### Что наружу не уходит

Имя файла проверяется участками, а не строкой целиком:

| Что пришло | Почему отказ 404 |
|---|---|
| `../etc/passwd`, `assets/../../etc` | шаг вверх участком; `v1..2.js` при этом — обычный файл |
| `//etc/passwd` | пустой участок — признак абсолютного пути |
| `assets//app.js`, `assets/` | пустой участок |
| `.env`, `.git/config` | участок с ведущей точкой — скрытый файл |
| `app.js%00.png` | нулевой байт обрывает имя в системном вызове |
| ссылка на `/etc/hosts` | ссылки не отдаются вовсе: `realpath` в `fio` нет, и путь опрашивается без раскрытия ссылки |
| каталог, сокет, устройство | отдаются только обычные файлы |

Отказ — 404, а не 403: клиенту всё равно, чего именно нет по этому
адресу, а разные ответы на «нет файла» и «не отдам» рассказывают ему
об устройстве диска.

Ссылка отвергается любая, и внутрь раздачи тоже: `realpath` в `fio` нет,
а отличить ссылку на соседний файл от ссылки на `/etc/passwd`
лексическим путём нельзя. Каталог-ссылка на пути (`public/build` →
чужой каталог) при этом работает: её завёл владелец узла, а не клиент.

Закодированный шаг вверх (`/build/%2e%2e/etc/passwd`) до раздачи
не доходит вовсе: `http.server` отвергает такой адрес своим 400
«invalid uri» ещё до роутера. Запросу, пришедшему не по сети —
`dispatch` таблицей, — раздача отвечает на него 404: хвост маршрута
приезжает уже раскодированным.

### Отказ «файла нет» и запасная страница

Отказ «файла нет» собирает сама раздача: пустотой отвечать нельзя (см.
выше), а знает о том, что файла нет, только она. Отдаёт она его парой,
как и 405, а не готовым ответом:

```lua
local serve = router.files({ root = 'public' })

serve({ method = 'GET', params = { path = 'none.css' }, headers = {} })
--> nil, { status = 404, message = 'нет такого адреса' }
```

Этот отказ рисует обработчик отказов приложения — тот же, что рисует
промах по адресу. Клиенту всё равно, чего по адресу нет, маршрута или
файла, и тело у обоих промахов одно; браузер, которому приложение рисует
страницу 404, получает её и на промах по файлу. Готовый ответ миновал бы
обработчик отказов, и на промах по файлу уходил бы JSON роутера. Роутер
пишет такой отказ в журнал так же, как промах по адресу, —
предупреждением, с опознавателем происшествия в записи и в ответе.

Слово лежит в самом отказе, а не только в ответе роутера: слой отказов
на маршруте (`errors.middleware()` пакета
[tnt-error](https://github.com/tnt-skein/tnt-error)) собирает ответ
из отказа раньше, чем роутер допишет своё слово, и отказ без слова назвал
бы своим общим «Запрос отклонён».

Свой ответ на промах задаётся настройкой `missing` — функцией запроса,
которая отвечает готовым ответом либо своим отказом парой; раздача
отдаёт его как есть. Вид всех настроек раздачи спрашивается при
объявлении маршрута, как и у самого роутера: `missing = 'потом'` дожил бы
до первого промаха по файлу и сорвался обращением к строке как к функции
внутри боевого запроса.

Панель рисует свои адреса сама: `/panel/nodes` открывают ссылкой,
и файла с таким именем нет. Поэтому есть `fallback` — что отдать вместо
отказа. Хвост у корня при этом ловит **все** адреса, в том числе те, под
которыми живёт API, и для них есть `except` — начала путей, под которыми
запасной страницы нет, а есть честный отказ:

```lua
router.get('/*path', router.files({ bundle = panel, fallback = 'index.html', except = { '/api' } }))
```

Без него клиент, ошибшийся в адресе API, получил бы первую страницу
с кодом 200 — то есть HTML там, где ждал JSON, — и разбирал бы её как
отказ. Начало сравнивается целыми участками: `/api` не накрывает
`/apiary`.

Второй случай — тот же спор про 405 — решён в самом дереве: **более
длинный путь важнее хвоста**. Дошёл спуск до узла, где адрес есть,
а способа нет, — хвост, объявленный выше, за этот адрес уже не отвечает,
и ответом будет 405 с перечнем способов, а не первая страница с кодом
200. Выбор между двумя решениями — «настройкой у раздачи» и «правилом
в дереве» — сделан так потому, что случаи разные: про статус способа
знает только дерево, а про то, какие адреса не про панель, — только тот,
кто её объявляет.

### Сжатие

Сжатия у раздачи своего нет: слой приходит настройкой, и приходит
готовым.

```lua
router.serve('/build', 'public/build', { compress = gzip_layer })
-- accept-encoding: gzip → то, что слой сделал с ответом раздачи
```

Слой — обычный слой `(request, next)`: раздача отдаёт ему запрос как
есть, её ответ — строкой либо кусками, а то и отказ парой — он получает
от `next`, а наружу уходит то, что вернул слой. Слой сжатия знает, какие
типы сжимаются, что делать с `vary` и меткой и как сжимать поток
кусками; вторая копия этих правил внутри раздачи разошлась бы с первой
молча. Роутер при этом не знает, чем сжимают, и работает там, где сжатия
в системе нет вовсе. Кому нужно сжимать всё, чем отвечает узел, ставит
тот же слой на вход роутера: `router.new({ entry = { gzip_layer } })` —
тогда настройка раздаче не нужна.

### Настройки раздачи

| Настройка | Что значит |
|---|---|
| `root` | каталог на диске, непустой; либо он, либо `bundle` — ровно один |
| `bundle` | файлы в памяти процесса: `{ ['app.js'] = '…' }` |
| `param` | имя хвоста в шаблоне маршрута; по умолчанию `path` |
| `index` | что отдать, когда путь не назван; по умолчанию `index.html` |
| `fallback` | что отдать вместо отказа: страница панели |
| `except` | начала путей, под которыми запасной страницы нет |
| `missing` | чем отвечать, когда файла нет: ответом или отказом парой; по умолчанию отказ 404 парой |
| `cache` | `cache-control` обычного файла; по умолчанию `no-cache` |
| `immutable` | вечный кэш файлам с отпечатком в имени; по умолчанию нет |
| `fingerprint` | образец отпечатка в имени; по умолчанию `[%-%.]([%w_%-]+)%.[%w]+$` |
| `in_memory` | больше этого, байт, файл уходит кусками; по умолчанию мегабайт |
| `chunk` | размер куска, байт, от 1 до 64 МБ; по умолчанию 64 КБ |
| `compress` | слой сжатия ответа: `(request, next)`, как всякий слой |
| `name` | имя маршрута — только у `serve`: `router.url('assets', { path = … })` |

## Обработчик не функцией

Обработчик маршрута — функция запроса. Запись иного вида —
`{ объект, 'метод' }`, строка `'имя@метод'` — роутер сам не толкует:
он отдаёт её настройке `resolve` при объявлении маршрута, а что она
значит, знает тот, кто собрал роутер: например, приложение разрешает
такие записи через свой контейнер зависимостей.

```lua
local r = router.new({
    resolve = function(handler)
        return handler[1][handler[2]]      -- { объект, 'метод' } → функция
    end,
})

r.get('/customers/:id', { customers, 'show' })
```

Разрешение идёт при объявлении, а не при первом запросе: опечатка в имени
метода падает при загрузке приложения. Без настройки запись не-функцией —
отказ «маршруту … нужен обработчик».

## Выход в сеть: только за обратным прокси

Роутер держит границу тела, но не заголовков: заголовки читает сам сервер
`http.server`, до роутера, и размер их не ограничивает никто. Настройка
`max_header_size` у рока объявлена и не действует, а срок простоя
ограничивает время чтения заголовков, но не объём. Заголовок в 64 МБ,
у которого нет конца, одно соединение присылает за пару секунд, и узел
держит его в памяти: на учении ниже память узла выросла на 128 МБ,
и после закрытия соединения процессу она не возвращается.

Поэтому **узел выходит в сеть только за обратным прокси**. От прокси
нужны три вещи:

- предел заголовков: строка запроса, каждый заголовок и все вместе;
- сроки на медленного клиента: заголовки целиком, пауза в теле, пауза
  в чтении ответа;
- срок простоя соединений к узлу короче `idle_timeout` узла. Тогда
  простоявшее соединение закрывает прокси, узел видит конец потока,
  и ошибки `failed to read request: Interrupted system call` в журнале
  нет. Закрой такое соединение первым узел, он записал бы её на каждое
  закрытие.

Порт HTTP узла снаружи закрывают так же, как iproto. Образец для nginx —
главное в нём:

```nginx
upstream tarantool_app {
    server 127.0.0.1:8080;
    keepalive 16;
    keepalive_timeout 30s;      # короче idle_timeout узла (60 с)
}

server {
    client_header_buffer_size 1k;
    large_client_header_buffers 4 8k;
    client_header_timeout 10s;

    client_max_body_size 1m;    # не больше max_body узла
    client_body_timeout 10s;

    send_timeout 10s;
    keepalive_timeout 30s;

    location / {
        proxy_pass http://tarantool_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
    }
}
```

Значения проверены учением: узел с роутером и сроками выше, перед ним
nginx 1.28 с этим образцом; учение сверяет, что прокси держит обещанное,
а без прокси дыры на месте.

| Что пришло к прокси | Ответ клиенту | Что дошло до узла |
|---|---|---|
| заголовок в 8100 байт | 200 | запрос |
| заголовок в 8200 байт | 400 «Request Header Or Cookie Too Large» | ничего |
| четыре заголовка по 7000 байт | 200 | запрос |
| пять заголовков по 7000 байт | 400 | ничего |
| строка запроса в 9000 байт | 414 | ничего |
| заголовок в 64 МБ без конца | 400, память узла не выросла | ничего |
| заголовки по байту раз в полсекунды | соединение закрыто через 10 с без ответа | ничего |
| тело ровно в `max_body` | 200 | тело целиком |
| тело на байт больше | 413 от прокси | ничего |
| тело кусками (`Transfer-Encoding`) | 200 | тело с `Content-Length` |
| тишина после ответа | — | соединение закрыто прокси, ошибки в журнале нет |

За прокси меняется и то, что видит приложение:

- **Полный адрес — из настройки `url`, а не из запроса.** `full_url`,
  `signed_url` с `full` и `canonical` дают один и тот же адрес за прокси
  и без него; заголовки `Host` и `X-Forwarded-*` роутер для этого
  не читает (см. «Адреса»). Прокси, отдающий приложение под своим путём,
  называется путём в `url`: подпись ссылки при этом сверяется по пути,
  который видит узел.
- **`peer` — адрес прокси, а не клиента.** Заголовков прокси
  (`X-Forwarded-For`) роутер не разбирает: им можно верить, только зная,
  что перед узлом стоит именно прокси, а это знает развёртывание, не роутер.
  Всё, что считают по адресу клиента, — неудачные попытки входа, аудит, —
  за прокси считается по одному адресу на всех.
- **411 не бывает.** Тело кусками прокси собирает сам и отдаёт узлу
  с длиной.
- **Отказы самого прокси — не отказы приложения.** 400, 413, 414 от nginx
  приходят его страницей (`text/html`), без `x-request-id` и без записи
  в журнале узла: запрос до узла не дошёл. Клиент API, который разбирает
  тело отказа как JSON, получит HTML; свои тела этих отказов задаются
  в прокси (`error_page`). Отказы узла прокси пропускает как есть.
- **Выгрузка потоком теряет обратное давление.** Ответ прокси по умолчанию
  буферизует и вычитывает поток с узла целиком, как бы медленно ни читал
  клиент: на учении клиенту, читающему 64 КБ/с, узел за четыре секунды
  отдал все 400 кусков по 64 КБ. Ответ потока, которому это важно,
  ставит заголовок `x-accel-buffering: no` — тогда узел отдаёт столько,
  сколько вмещают буферы по дороге (на учении — от 162 до 210 кусков
  из 400), и дальше идёт за клиентом:

```lua
return router.stream(produce, 200, { ['x-accel-buffering'] = 'no' })
```

Исправить сам рок — дело его владельцев (размер заголовков, ошибка
журнала на закрытии по сроку, `idle_timeout` из `roles.httpd`, тело
и длина ответа на HEAD). Своей копии рока с заплатками пакет не держит.

## Опасные места

- **Размер заголовков на узле не ограничивает никто.** Ни роутер —
  заголовки читает сервер до него, — ни сервер: `max_header_size` у рока
  не действует. Узел, открытый клиентам напрямую, одно соединение
  заставляет держать в памяти сколько угодно. В сеть узел выходит только
  за обратным прокси с пределом заголовков и сроками — см. «Выход в сеть».
- **`attach` подменяет обработчик сервера целиком.** Собственные маршруты
  и статика `http.server` после этого не работают. Это осознанно: иначе
  сервер снова сравнивает путь образцом по одному, ради чего дерево
  и написано.
- **HEAD обслуживается обработчиком GET**: заголовки те же, тело пустое.
  Длину роутер называет сам — `content-length` тела-строки, которое
  вернул бы GET, — а названную обработчиком (раздача знает размер файла,
  не открывая его) оставляет как есть; у потока длины заранее не бывает,
  и заголовка у него нет. Это то, что отдаёт `dispatch`; **до клиента
  по сети доезжает ноль**: `http.server` 1.9.1 пересчитывает
  `content-length` по телу, которое пишет в сокет, и затирает названное
  обработчиком. Пока рок этого не правит, длину ответа узнают запросом
  GET, а не HEAD. У потока источник на HEAD не зовётся вовсе, а раздача
  файлов не открывает большой файл и не читает его кусками. Под слоем
  сжатия длина у HEAD — длина несжатого ответа: сжимать нечего,
  и сжатой длины не знает никто; `content-encoding` слой на HEAD
  не ставит, а метку и `vary` ставит те же, что у GET.
- **Закодированный шаг вверх не доходит до узла**: `/build/%2e%2e/etc`
  сервер отвергает своим 400 «invalid uri» ещё до роутера, и в журнале
  узла об этом ничего нет. Раздача отвечает на такой путь 404 только
  тогда, когда запрос пришёл не по сети (`dispatch` таблицей).
- **Срок простоя ставит сервер, а не роутер.** `attach` предупреждает
  о сервере без `idle_timeout`, но срока за владельца не выбирает. Каждое
  соединение, закрытое по сроку — и простоявший keepalive тоже, —
  `http.server` пишет ошибкой `failed to read request: Interrupted system
  call`: слово ядра неверное, это истёкший срок, и на узле с живыми
  клиентами таких записей много. За прокси их нет: простоявшее соединение
  к узлу закрывает прокси, раньше срока узла (см. «Выход в сеть»).
  `roles.httpd` 1.9.1 `idle_timeout` серверу не передаёт вовсе — его
  ставит роль, вешающая маршруты.
- **Ушедший клиент поток не останавливает сразу.** Сервер узнаёт об этом
  только на записи куска и выходит из цикла — источник просто больше
  не зовут. Закрыть курсор или отпустить блокировку ему не на чём,
  поэтому ничего такого источник между кусками не держит. Итоговой
  записи у такого потока нет: ни «отдан», ни «оборван» — сказать
  о конце некому.
- **Источник потока идёт в контексте своего запроса.** Его обращения
  к соседям уносят `x-request-id` и `traceparent` запроса, а их отрезки
  трассы становятся детьми серверного отрезка, который к этому мигу уже
  закончен: отрезок сервера кончается с возвратом обработчика, а не
  с концом потока.
- **Ошибки объявления бросаются сразу**, при загрузке приложения:
  обязательный участок за необязательным, безымянный хвост, повторное имя
  маршрута, слой, объявленный именем там, где `tnt.middleware` нет,
  настройка не того вида — и у роутера, и у раздачи. Узел, поднявшийся
  с кривым маршрутом, обнаружил бы это первым запросом в бою.
- **Отказ объявления показывает на строку, где его написали.** Опечатка
  в шаблоне, незнакомое ограничение, маршрут, объявленный дважды,
  повторное имя, незнакомое имя слоя, начало группы без косой черты,
  обработчик отказов не функцией, негодный предел или не тот сервер
  у `attach` винят строку, которая позвала способ роутера:

  ```lua
  router.get('/customers/:id?/orders', list)   -- app/http.lua:12
  -- ошибка: app/http.lua:12: за необязательным участком
  --         в «/customers/:id?/orders» стоит обязательный
  ```

  Настройки `router.new` и `router.configure`, настройки и тело `group`,
  настройки раздачи — `serve` и `router.files` — винят так же строку
  вызова: у группы одно место на всё — тело, настройки и начало пути,
  у `serve` — и на настройки раздачи, и на её маршрут. Строка внутри
  пакета отправила бы искать ошибку в нём. Отказ маршрута в теле группы
  называет строку маршрута, а не группы. Слои входа общего роутера
  собираются при первом обращении — пакет слоёв настраивают и после
  роутера, — и отказ их сборки винит строку, которая обратилась к общему
  роутеру первой. Функции `resolve` и `wrap`, винящие своего вызывающего
  (`error(текст, 2)`), тоже называют строку маршрута. Вызов, стоящий
  хвостом (`return router.get(…)`), своего кадра не оставляет, и место
  уходит к тому, кто позвал функцию с ним.
- **`dispatch` не бросает исключений вовсе**: падение обработчика, падение
  обработчика отказов и его молчание — всё это 500 с опознавателем.
  Один запрос не должен ронять узел. Бросает только тело `stream`,
  и только серверу, посреди отправки: иначе оборванный поток не
  отличить от целого.
- **`int` — это цифры со знаком**, а не всё, что `tonumber` прочтёт
  числом: `0x10` и « 7» адресами не считаются. `alpha` — только латиница:
  образцы Lua считают байтами, а не буквами.
- **Имени и типу присланного файла верит только клиент.** `client_name` —
  байты, как их прислали: там бывает и `../../etc/passwd`,
  и `C:\Users\...`, и нулевой байт, и не UTF-8. На диск кладут `name`,
  а `type` — это то, что клиент написал в заголовке части: сверить его
  с содержимым роутер не может и не делает вид, что сверил. Кому нужна
  уверенность — смотрит первые байты сам.
- **Временный файл живёт до конца обработки запроса.** Уборка идёт сразу
  после ответа, и поток, который собрался читать временный файл уже
  на отправке тела, прочтёт его только потому, что открытый файл
  переживает `unlink`; открывать его заново поздно. Файл, нужный дольше
  ответа, переносят `move`.
- **Перенос переименованием не сброшен на диск.** Содержимое временного
  файла писатель `tnt-fs` сбросил ещё при приёме, а запись о нём
  в каталоге места `move` не сбрасывает: отключение питания сразу после
  ответа может оставить место пустым. Копия на другой том и запись
  из памяти ложатся подменой `tnt-fs` — со сбросом файла и каталога.
  Кому нужна долговечность всяким путём, кладёт файл в хранилище сам:
  `tnt-fs.replace` или ведро `tnt-s3`.
- **Временный файл сбрасывается на диск, хотя живёт один запрос.**
  Писатель `tnt-fs` в конце части сбрасывает на диск и файл, и каталог:
  выключателя у него нет намеренно. На `/tmp` в памяти (tmpfs) это ничего
  не стоит, а на диске — два сброса на каждый присланный файл больше
  `in_memory`. Узлу, которому это дорого, каталог временных файлов
  называют в памяти: `temp_dir`.

## Чем пришлось поступиться

- **Метка страницы стоит целой страницы.** 304 бережёт сеть и клиента,
  но не узел: метка — отпечаток тела, и тело для неё рисуется на каждый
  запрос. Не рисовать вовсе может только обработчик, который знает
  версию своих данных: он сверяет `if-none-match` сам и отвечает 304
  до страницы. Какая версия у страницы, знает приложение, а не роутер.
  Сверяет он функцией `tnt.router.files.caching.matched`, а не
  равенством строк: браузер присылает список меток, а под слоем сжатия
  клиент с gzip получает метку слабой и присылает её назад с пометкой
  `W/` — равенство строк ответило бы ему 200 с телом.

  ```lua
  local caching = require('tnt.router.files.caching')

  caching.matched('W/"7c2a"', '"7c2a"')              --> true
  caching.matched('"1f0b", W/"7c2a"', '"7c2a"')      --> true
  caching.matched('*', '"7c2a"')                     --> true
  caching.matched('"7c2b"', '"7c2a"')                --> false
  ```
- **Общие данные страниц достаются только ответу на запрос.** Помощник
  страниц зовут без запроса, и `view_data` берёт его из хранилища файбера,
  куда роутер кладёт его на время ответа. Страница, нарисованная
  в файбере, который завёл обработчик, общих данных не получает: запрос
  живёт у файбера ответа, а переносить его в каждый порождённый файбер
  значило бы держать запрос, пока жив файбер. Такой обработчик считает
  данные сам, до файбера, и отдаёт их аргументом.
- **Кусок по заголовку выбирает обработчик.** Своего заголовка
  «дай кусок» у роутера нет: какие куски у страницы можно отдавать
  отдельно, знает её обработчик, и список он держит сам. Общее правило
  выбора по заголовку отдавало бы любой кусок любой страницы, в том
  числе тот, что рамка не показывает.
- **Пустота от обработчика — 500, а не 404.** Обработчик, который
  возвращает `nil` вместо «нет такого», отвечает 500: «нет такого»
  и «потерял ответ» были бы одним и тем же `nil`, и различить их роутеру
  нечем. Чинится это одной строкой — вернуть готовый ответ, — но найти
  такие места можно только чтением кода, а не проверкой.
- **Промах по файлу пишется в журнал.** Отказ «файла нет» раздача
  отдаёт парой, и роутер пишет его, как всякий отказ: предупреждением,
  а не ошибкой, — тревоги промах не стоит. Сканер, перебирающий имена
  файлов, оставляет по строке на каждое имя. Кому эти строки не нужны,
  задаёт `missing` с готовым ответом: такой ответ роутер отдаёт как есть
  и не пишет, но и обработчик отказов приложения его тогда не рисует.
- **Довесок приложения переносится по списку занятых имён, а не по
  объявленному списку полей.** Опечатка в имени поля не будет замечена:
  `identtity` приедет в обработчик ровно так же, как `identity`, — просто
  никто её там не прочитает. Обратное — объявить перечень разрешённых
  полей — потребовало бы от каждого приложения объявлять свои поля
  роутеру, который ими не пользуется.
- **Правило «длинный путь важнее хвоста» отнимает у хвоста часть
  адресов.** Хвост `/files/*path`, объявленный на все способы, больше
  не ответит на `POST /files/new`, если `/files/new` объявлен только
  на GET: там 405. Для раздачи статики это правильно, для хвоста,
  написанного как всеядный посредник, — нет, и такому посреднику придётся
  объявить нужные способы самому. Заодно это правило делает `Allow`
  неполным: `GET /a/b` при `/a/b` на POST и `/a/*rest` на GET получит
  `Allow: OPTIONS, POST`, хотя GET по этому адресу хвост обслужил бы.
  По RFC 9110 `Allow` называет способы адреса, и клиент по нему решает,
  чем ходить, — то есть перечень говорит правду о маршрутах узла, а не
  обо всех способах адреса.
- **Свой обработчик отказов зовётся после записи в журнал.** Уровень
  записи выбран по статусу, с которым отказ дошёл до `refuse`: 5xx —
  ошибка, всё прочее — предупреждение. Если обработчик ответит другим
  статусом, в журнале это всё равно останется прежним уровнем. Уровень
  выбирается правилом, а не перечнем кодов: статус приходит и от
  обработчика, назвавшего свой код, и перечня на все такие коды нет.
- **`nil, err` от обработчика — не непременно 500.** Отказ, назвавший
  свой статус по договору границы, уходит с ним: 410, а не 500. Цена —
  таблица с числовым `status` из чужого кода, возвращённая как отказ,
  уходит клиенту своим статусом. Обратное — отвечать на всё 500 —
  означало бы, что обработчик отказов приложения, поставленный одной
  строкой, молча понижает каждый ожидаемый отказ обработчика
  до внутренней поломки.
- **Тело запроса, пришедшее через `attach`, всегда строка.** Без
  `Content-Length` это пустая строка, а не `nil`, — как у самого сервера.
  Тело больше мегабайта без явного `max_body` получает 413: предел
  по умолчанию — мегабайт, и приложение с загрузкой файлов называет свой.
- **Поле `code` в теле отказа есть не у всех.** Оно есть у тех отказов,
  что пришли из каталога приложения, и у отказа подписанной ссылки
  (`router_signature_invalid`, `router_signature_expired`): подделку
  и устаревшую ссылку приложение показывает по-разному, а номер у них
  один. У отказов, которые роутер собирает сам, — 404, 405, тело
  не в пределах, — кода нет: клиент различает их статусом.
- **Подпись ссылки не держит узла и способа.** Ссылка, подписанная для
  `GET /invoices/7`, откроет и `DELETE /invoices/7`, если слой стоит
  на обоих маршрутах, и откроется на любом узле с тем же ключом. Первое —
  цена ссылки «отписаться», которую открывают и GET, и POST; второе —
  цена прокси, за которым узел не знает своего имени. Где это важно,
  слой ставят на маршрут одного способа, а приложению на своём узле
  дают свой ключ.
- **Внутри срока ссылка открывается сколько угодно раз.** Подпись
  не помнит, что по ней уже ходили: это знает только хранилище,
  а роутер его не держит. Одноразовое действие по ссылке делают
  повторяемым (подтверждение почты второй раз ничего не меняет) либо
  помнят подпись у себя — она лежит в `request.query.signature`.
- **Поле, дописанное к ссылке после подписи, её ломает.** Метки рассылок
  (`utm_source`), которые почтовая служба дописывает к ссылкам письма,
  меняют строку запроса, и подпись не сходится. Письма с подписанными
  ссылками уходят с выключенной разметкой ссылок; снять метки до сверки
  роутер не берётся — список «безвредных» полей был бы дырой, через
  которую в подписанное попадает непроверенное.
- **Настройки общего роутера проверяются в `configure`,** а не при первом
  обращении: негодный адрес приложения или короткий ключ винят строку
  настройки, а не первый запрос.
- **Список в строке запроса собирается повторённым именем, а словарь
  выпадает.** `url(name, nil, { tag = { 'a', 'b' } })` и адрес запроса
  `request.url` с повторённым полем дают `tag=a&tag=b`, а таблица
  не списком (`{ a = 1 }`) в адрес не ложится и выпадает: общего вида
  вложенных полей в строке запроса нет, и свой разобрал бы только этот
  роутер.
- **Тело многочастной формы обработчику не достаётся.** У запроса
  с `multipart/form-data` `request.body` — пустая строка: тело разобрано
  на поля и файлы прямо из соединения, и второй его копии нет нигде.
  Разобрать такое тело по-своему обработчику нечем, у него есть только
  `request.form` и `request.files`; обратное — держать в памяти форму
  с вложением на десятки мегабайт — и есть та дыра, ради которой разбор
  сделан потоковым.
- **Тело `application/x-www-form-urlencoded` разбирается всегда**,
  даже если обработчику нужно только сырое тело. Само тело при этом
  остаётся в `request.body`: разбор его не съедает, но пределы полей
  к нему применяются, и форма из тысячи полей получает 413, даже если
  обработчик прочёл бы её строкой.
- **Расширенная запись имени файла (RFC 5987, `filename*`) не читается**,
  а транспортный отступ за границей (RFC 2046) не принимается. Первое
  запрещает RFC 7578 (§4.2) в самой форме, второго не шлёт ни один
  клиент, — а лишняя ветка в разборе границы это лишний способ принять
  за границу то, что ею не было.

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`,
по файлу на модуль. Запрос и ответ — таблицы, поэтому почти всё
проверяется без сервера, через `dispatch`. Стык с `http.server` — тело
с пределом и сроком, форма потоком, ответ по кускам, смена протокола,
полный адрес за приложением под своим путём — проверяется живым сервером
на петле и `http.client` (`server_test.lua`, `address_server_test.lua`,

Часы, случайность и подключение соседей подменяются как внешние
зависимости, файловая система — подменой `fio` под `tnt-fs`: роутер зовёт
фасад как есть, и отказ диска проходит тот же разбор, что и в бою.
Записи журнала ловит ловушка на `tnt-log`.
Ограничения и слои, названные именем, проверяются против настоящих
`tnt-validate` и `tnt-middleware`, а запасной путь без них — подменой
подключения соседей. Слой сжатия у раздачи проверяется двойником: роутер
отдаёт ему запрос и свой ответ и возвращает то, что слой с ответом
сделал. `router_test.lua` проверяет связку с обработчиком отказов
`tnt-error` против установленного пакета — `make deps` ставит его рядом
с соседями, — а без него эту проверку пропускает.
